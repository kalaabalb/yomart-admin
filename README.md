# YoMart Admin Web

Deployed staging admin: https://yomart-admin.onrender.com. Shared release, security, operations, and tester guidance: https://github.com/kalaabalb/yomart-docs.

React/Vite web admin for managing the YoMart storefront.

## Run locally

```bash
cp .env.example .env
npm install
npm run dev
```

Open the address printed by Vite (normally `http://localhost:5173`). The local `.env` points to `http://localhost:3000`.

Sign in with an existing administrator account provisioned by the backend. Admin JWTs are kept in browser `sessionStorage` and checked against `/admin-users/profile` at startup. No sample products, sales, categories, orders, or accounts are generated by this UI.

Do not add usernames, passwords, JWT secrets, or other private credentials to a Vite environment file. `VITE_*` values are bundled into browser code. Provision administrator accounts through the backend's protected admin workflow or its server-side environment configuration.

## Current screens

- Dashboard: totals and recent activity are derived from the live products, orders, categories, and users APIs. The sales graph groups real order totals by date.
- Catalog: products with up to five image uploads, categories, subcategories, and brands.
- Storefront: banners, curated collections, and store/payment settings.
- Fulfillment: order details, status/tracking updates, and payment proof review.
- Admin users: shown only to super admins, matching the server's access rules.

The interface has responsive desktop, tablet, and mobile layouts, plus persisted light/dark theme selection. Unsupported or unavailable API data is shown as an error or empty state rather than being replaced by mock data.

## Build

```bash
YOMART_BUILD_ENV=staging \
VITE_API_BASE_URL=https://<confirmed-staging-api-origin> \
VITE_EXPECTED_SITE_ORIGIN=https://<confirmed-staging-admin-origin> \
YOMART_EXPECTED_API_ORIGIN=https://<same-confirmed-staging-api-origin> \
YOMART_PRODUCTION_API_ORIGINS= \
YOMART_NO_PRODUCTION_API=true \
YOMART_PRODUCTION_SITE_ORIGINS=https://<production-admin-origin>,https://<production-storefront-origin> \
npm run build
```

The `npm run build` wrapper validates configuration, removes any previous `dist/` before preflight, and removes partial output on failure. It validates the built text artifacts contain the selected API and admin-site origins and no localhost/placeholder endpoints. The production bundle refuses to run when opened at an origin other than `VITE_EXPECTED_SITE_ORIGIN`. Build with `YOMART_BUILD_ENV=staging` or `production`, `VITE_API_BASE_URL`, `VITE_EXPECTED_SITE_ORIGIN`, and a matching `YOMART_EXPECTED_API_ORIGIN`. For the current Render staging setup, set `VITE_API_BASE_URL` and `YOMART_EXPECTED_API_ORIGIN` to the same confirmed staging API origin, and set `VITE_EXPECTED_SITE_ORIGIN` to the confirmed admin Static Site origin. If no production API exists, leave `YOMART_PRODUCTION_API_ORIGINS` empty and set `YOMART_NO_PRODUCTION_API=true`; the latter is an explicit owner assertion used if the hosting dashboard omits blank variables. A non-empty production API list and `YOMART_NO_PRODUCTION_API=true` are rejected together. If production APIs exist, omit/set the flag to `false` and supply only confirmed production API origins, comma-separated. Every non-empty list entry must be a bare HTTPS origin; paths, wildcards, credentials, query strings, and fragments are rejected. For staging, `YOMART_PRODUCTION_SITE_ORIGINS` may be empty or unset when no production website origins are confirmed. If origins are supplied, each is strictly validated and staging/production overlap is rejected. An empty list cannot detect overlap with an unknown production website, so add confirmed origins when they become known. Production builds remain strict and require non-empty, valid `YOMART_STAGING_API_ORIGINS` and `YOMART_STAGING_SITE_ORIGINS`. The build rejects mismatches, loopback API/site hosts outside local mode, placeholder hosts, and origins listed for the opposite environment. These values are public, not secrets. Configure the Express CORS allowlist to include the deployed admin site origin.

Render Static Site staging environment variables:

```text
YOMART_BUILD_ENV=staging
VITE_API_BASE_URL=https://yomart-api.onrender.com
YOMART_EXPECTED_API_ORIGIN=https://yomart-api.onrender.com
VITE_EXPECTED_SITE_ORIGIN=https://yomart-admin.onrender.com
YOMART_PRODUCTION_API_ORIGINS=(empty or unset)
YOMART_NO_PRODUCTION_API=true
YOMART_PRODUCTION_SITE_ORIGINS=(empty or unset until production website origins are confirmed)
```

Do not copy the staging admin origin into the production site denylist or invent production origins. When confirmed production sites exist, list their HTTPS origins here; a staging-site overlap will fail validation. An empty list cannot detect overlap against a production hostname that has not been identified.

To make a local release preview against the local backend, use:

```bash
YOMART_BUILD_ENV=local VITE_ALLOW_LOCAL_API=true VITE_API_BASE_URL=http://127.0.0.1:3000 VITE_EXPECTED_SITE_ORIGIN=http://localhost:5173 YOMART_EXPECTED_API_ORIGIN=http://127.0.0.1:3000 npm run build
```

## Backend contract

This admin uses the existing Express routes in `yomobiles_backend`: `/admin-users`, `/products`, `/categories`, `/subCategories`, `/brands`, `/posters`, `/collections`, `/orders`, `/users`, `/store-settings`, and `/health`. Mutations continue to be validated and authorized by the backend. For example, store settings and admin account management require super admin privileges.

Product and category/banner images are resized to a 2400-pixel maximum edge and compressed to WebP in the browser before upload when this reduces size; the backend validates and normalizes them again. The upload limit is 10 MB per image. Product records preserve separate image slots supported by the backend.
